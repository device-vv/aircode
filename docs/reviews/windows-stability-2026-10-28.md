# AIRcode: проверка устойчивости редактора в Windows

Дата: 28 октября 2026. Основа: `main`, `f3a9bb9`. Рассмотрена ветка `origin/fix_update_by_Roma`, `0854e53`.

Реализацию выполнил Kimi K3.1 Pro через `kimi-delegate`. GPT исследовал причины, отобрал изменения и выполнил независимую проверку. Коммиты, push, merge и публикация релиза не выполнялись.

## Найденные проблемы

1. Область `DocumentView` растягивается по высоте документа. Поэтому вертикальная прокрутка не получает ограниченный viewport. Это воспроизведено на настоящем элементе GPUI в тестовом окне 640×360.
2. У длинных строк нет горизонтального диапазона прокрутки. Это также воспроизведено тестом GPUI.
3. Разделители панелей используют экранный `window.bounds().origin` вместе с локальными координатами мыши и получают движение только в узкой области разделителя.
4. Перетаскивание заголовка вызывает синхронный `SendMessageW` внутри обработчика GPUI. Это потенциальный путь повторного входа в состояние приложения при перемещении/смене DPI. Исходный вылет на другом ПК не воспроизведён.
5. IME переводит относительное выделение составляемого текста через весь документ. Для добавления `🙂` после `prefix` фактическое выделение `10..10` вместо `6..10`; воспроизведено через `EntityInputHandler`.
6. Номера строк используют фиксированную длину текстового стиля 4, которая не соответствует пятизначным номерам.
7. Обработчик потока ИИ считает обрыв соединения успешным завершением и не обрабатывает последний буфер SSE при EOF.
8. При открытых настройках клавиатурный ввод остаётся в документе: тест получил `safeqa` вместо неизменённого `safe`.
9. При сохранённых ширинах панелей 450/650 px окно 960 px оставляет редактору 0 px; перетаскивание разделителя за его узкую область перестаёт менять ширину. Оба сценария воспроизведены тестами GPUI.
10. Предложение переключить язык использует одну строку flex без ограничения ширины текста. В текстовой системе тестового GPUI сообщение занимает 530 px внутри диалога 520 px ещё до кнопок и отступов. В верхней панели при 960 px часть кнопок выходит за окно и на английском, и на русском.

## Базовая проверка

- `cargo test --workspace --locked`: 42 теста прошли до изменений. Для mock HTTP нужен разрешённый localhost; обычная песочница блокирует сетевые тесты.
- Отдельный стенд `target/qa/ui-harness`: 13 проверок падают на сохранённом исходном UI `f3a9bb9`. Проверены viewport, две оси прокрутки, курсор, попадание мышью после горизонтальной прокрутки, IME, минимальная ширина редактора, движение разделителя/ползунка, защита ввода, первый запуск, узкая панель ИИ, подсказки полей и раскладка переводов. Результат: `target/qa/baseline-ui.log`.
- Синтетический файл `target/qa/scroll-large.rs`: 12 050 строк, CRLF, кириллица, emoji, длинная строка; 809 223 байта.
- Исходная Windows-сборка запускается и открывает штатный диалог файлов. Помощник захвата экрана возвращает `D3D11CreateDevice failed (0x80004005)`; доступно только дерево системных элементов Windows. Пиксельная проверка через этот помощник не выполнена.

## Отбор из ветки Романа

Использованы подходы к индексу строк, CRLF/Unicode/IME, моноширинному шрифту, защите ввода и фокуса, обработке EOF/ошибок потока, тайм-ауту чтения и диагностике паник. Они адаптированы к текущей основе и проверены. Полное слияние не выполнялось: ветка удаляет `Cargo.lock`, содержит более широкие изменения интерфейса/undo и повторный вызов `emit_tool_calls`. `Cargo.lock` сохранён; добавлено девять зависимостей тестовой поддержки GPUI без обновления прежних версий пакетов.

Редактор получил ограниченный viewport, вертикальную и горизонтальную прокрутку с ползунками, видимость курсора и переходы Page Up/Down, Ctrl+Home/End. ## Пределы проверки

- Исходный вылет на другом рабочем ПК не воспроизведён. Перетаскивание между физическими мониторами, особенно с разным DPI/масштабом, **не подтверждено**. Для утверждения, что именно этот вылет устранён, нужен запуск сборки на том ПК.
- Захват экрана недоступен из-за ошибки помощника D3D11. Пиксельная проверка и визуальная оценка удобства на реальном экране не выполнены. Стенд использует настоящие элементы и события GPUI с тестовой текстовой системой; он не заменяет проверку реальных шрифтов на экране.
- Сетевые сценарии ИИ проверены локальным HTTP mock. Реальные платные запросы провайдерам не отправлялись, ключи и учётные записи не изменялись.
- Журнал паник не гарантирует диагностику аварии графического драйвера или принудительного завершения процесса.

## Проверка на проблемном ПК

1. Открыть большой файл кода в оконном режиме, несколько раз перенести окно за заголовок между мониторами в обе стороны. Повторить с несохранённым изменением и проверить сохранность текста.
2. Проверить перенос между мониторами с одинаковым и разным масштабом, если такая конфигурация есть. Записать версии Windows, драйвера видеокарты и масштаб каждого экрана.
3. Прокрутить длинный файл колёсиком, тачпадом и ползунком; проверить длинную строку, Page Up/Down, Ctrl+Home/End, ввод после прокрутки.
4. Уменьшить окно, изменить ширину обеих боковых панелей, снова увеличить окно. Проверить удобную ширину кода и возврат предпочтительных размеров панелей.
5. Открыть настройки из редактора, ввести текст в поле, закрыть настройки и продолжить редактирование. Код под настройками должен оставаться неизменным.

При повторном вылете приложить новый диагностический журнал кандидата: `%LOCALAPPDATA%\AIRcode\crash.log`. Записываются версия, время, место паники и стек; текст паники намеренно исключён, поскольку он может содержать пользовательские данные. Содержимое рабочих файлов и API-ключи для диагностики не требуются.
